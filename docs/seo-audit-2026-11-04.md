# SEO audit: Colorion Animated Buttons

Audit date: November 4, 2026. Site: [animatedbuttons.colorion.co](https://animatedbuttons.colorion.co/).

**Build a small hierarchy of useful collections and effect pages. Keep the current homepage as the main gallery.** The largest growth opportunity is to give distinct search needs their own destinations. First, fix the live server's response for missing files and pages.

This audit covers the source, a production build, live HTTP responses, one mobile Lighthouse run, and selected competing resources. No application or hosting settings changed. Search Console, private analytics, backlink data, and paid keyword volumes were unavailable. Keyword priorities below are hypotheses based on content fit and observed search results. They are not measured demand or traffic forecasts.

**Mobile Lighthouse, one simulated run:** performance 99/100, SEO 92/100, accessibility 94/100. Largest Contentful Paint was 1.7 seconds. Total Blocking Time was 0 milliseconds. Cumulative Layout Shift was 0. The SEO failure was invalid `robots.txt`, with 474 parser errors caused by the returned HTML.

These are lab results, not field Core Web Vitals. The SEO score does not measure topic coverage, search demand, backlinks, or the value of the site structure. Good performance does not guarantee rankings. [Google's page-experience guidance](https://developers.google.com/search/blog/2023/04/page-experience-in-search) explains this limit.

## 2. Fix the crawl foundation first

### A. Replace the homepage fallback for unknown paths

The test path `/seo-audit-missing-page-20261104/` returns the complete homepage with status 200. Its canonical points to `/`. This is a confirmed response defect. Search Console data is necessary to determine whether Google reports affected URLs as soft 404s or duplicate pages.

Configure the static host to serve actual generated files and directories. Return HTTP 404 for unknown paths. A friendly `404.astro` page helps visitors, but the host must also return the correct status. Do not redirect every missing URL to the homepage.

Acceptance checks:

- `/` returns 200 and the homepage.
- A generated effect route returns 200 and its own content when opened directly.
- A random missing route returns 404, including after a browser refresh.
- A missing asset returns 404 instead of HTML under a CSS, JSON, or image URL.

The repository has no host routing configuration that identifies the fallback rule. The serving layer needs inspection during implementation. HTTP status semantics matter independently of canonicals. [Google's status-code guidance](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes) describes the indexing behavior.

### B. Publish real robots and sitemap files

Add `public/robots.txt`. An appropriate initial file, once the sitemap exists, is:

```text
User-agent: *
Allow: /

Sitemap: https://animatedbuttons.colorion.co/sitemap-index.xml
```

Generate a sitemap from published, canonical HTML routes. The configured `site` value already supplies the correct origin. Include collections, effect pages, guides, and the homepage. Exclude JSON data, unpublished pages, customization states, and redirects. Use accurate modification dates only when the content changes.

Serve robots as plain text and sitemaps as XML. Submit the actual sitemap URL in Search Console. A sitemap helps discovery. It does not guarantee indexing or improve rankings on its own. [Google's sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview) describes its purpose.

The current malformed robots response does not prove that the site is blocked from indexing. A missing robots file alone would not block indexing either.

### C. Correct the broken Colorion tool link

The header points to `https://csstooltips.colorion.co`, which failed DNS resolution during this audit. `https://tooltips.colorion.co/` returned 200 with the CSS Tooltip Library title. Update the destination in `src/pages/index.astro:18` after checking that this is the intended tool. This is a small navigation fix, not a major ranking opportunity.

## 3. Proposed information architecture

Keep `/` as the broad CSS animated-button gallery. Add six focused collections and a limited set of substantial effect pages. Add guides where users need an explanation rather than a gallery.

```text
/
├── collections/
│   ├── glow-buttons/
│   ├── fill-buttons/
│   ├── border-buttons/
│   ├── 3d-shadow-buttons/
│   ├── text-icon-buttons/
│   └── motion-buttons/
├── effects/
│   ├── glow/
│   ├── sliding-fill/
│   ├── border-draw/
│   ├── shine-sweep/
│   └── ...selected distinct effects
├── guides/
│   ├── css-button-hover-effects/
│   ├── accessible-button-animations/
│   └── customize-css-buttons/
└── tools/
    └── button-generator/  [later, if it becomes a real tool]
```

The directory names support maintenance. Their depth does not create a ranking benefit by itself. Descriptive URLs, useful content, and links between the pages do the work.

**Do not add a second broad `/css-buttons/` gallery that copies the homepage.** Give each page a clear purpose:

| Page type | User need | Content that distinguishes it |
|---|---|---|
| Homepage | Browse free animated CSS buttons | Overview, collection navigation, full gallery, selected guides |
| Collection | Compare a family of effects | Curated demos, differences, selection advice, links to implementations |
| Effect | Copy and understand one implementation | Complete code, focused demo, variants, customization and limitations |
| Guide | Learn how or solve a problem | Original explanation, working examples, troubleshooting |
| Generator | Create a customized button | Useful controls, live preview, valid export, shareable settings |

For example, the glow collection targets comparison across glow styles. The glow effect page explains one implementation. A guide explains how hover transitions work. Avoid three pages that all repeat the same introduction and snippet.

| Proposed route | Query themes to validate | Existing material | Editorial role |
|---|---|---|---|
| `/collections/glow-buttons/` | CSS glow buttons, neon button effects | Glow, Neon Edge, Neon Flicker, Ring Pulse | Compare soft glow, border glow, and animated light |
| `/collections/fill-buttons/` | CSS button fill animation, sliding hover effects | Fill directions, Radial, Split Half, Skew Wipe, Wave | Compare direction, origin, clipping, and text contrast |
| `/collections/border-buttons/` | CSS button border animation, outline hover effects | Border Draw, Corners, Outline Pop, Outline Grow, Double Edge | Explain border, outline, and pseudo-element approaches |
| `/collections/3d-shadow-buttons/` | CSS 3D buttons, button shadow hover effects | Press, Lift, Hard Shadow, Brutalist, Long Shadow | Compare press, depth, and shadow techniques |
| `/collections/text-icon-buttons/` | CSS arrow button animation, underline button effects | Arrow Push, Arrow Ring, Icon Push, Underline, Marker | Compare label, icon, and underline motion |
| `/collections/motion-buttons/` | CSS bounce button, pulse button animation | Pulse, Bounce, Wobble, Jelly, Shake, Tilt | Compare movement, duration, and reduced-motion behavior |

Each collection needs a short explanation of the family, genuine selection advice, and links to relevant implementations. Shared base styles and a few repeated demos are reasonable. Changing only a title and filter is insufficient editorial value.

Start with glow, fill, and border. They map directly to the current library and have clear visual differences. Validate their relative demand with Search Console and a keyword tool before setting a large content budget.

## 5. Publish selected effect pages, then expand

**Start with about 12 distinct implementations. Do not automatically publish 99 thin pages.** A useful first batch is:

| Route | Existing effects to use | Specific value |
|---|---|---|
| `/effects/glow/` | Glow | Explain layered shadows and glow color |
| `/effects/neon-edge/` | Neon Edge | Explain inset glow and the bright border |
| `/effects/sliding-fill/` | Fill Up, Down, Left, Right | One implementation with directional variants |
| `/effects/radial-fill/` | Radial, Ink Spread | Explain expansion and clipping differences |
| `/effects/border-draw/` | Border Draw | Explain the clipped border overlay |
| `/effects/corner-border/` | Corners | Explain corner marks and expansion |
| `/effects/shine-sweep/` | Shine Sweep, Tilt Shine | Explain sheen variants and their rendering cost |
| `/effects/press/` | Press | Explain depth, hover, and an optional active state |
| `/effects/brutalist/` | Brutalist, Hard Shadow | Explain a solid offset shadow and press behavior |
| `/effects/arrow-push/` | Arrow Push, Arrow Ring | Explain icon movement and accessible labeling |
| `/effects/pulse/` | Pulse, Ring Pulse | Compare pulse types and motion controls |
| `/effects/glitch/` | Glitch | Explain stepped keyframes and motion limitations |

Publish separate variant pages only when their implementation or user need warrants it. For example, Fill Up and Fill Down share most of their code. A single useful directional-fill page can serve both needs.

The current “Magnetic” effect only lifts and scales on hover. It does not follow the pointer (`src/data/buttons.ts:349`). Do not target pointer-tracking magnetic-button queries with that implementation. Link to the relevant Kinetics resource instead. The current Ripple is a centered hover effect, not a click-position ripple (`src/data/buttons.ts:162`). Describe that distinction if a ripple page follows.

### Minimum useful effect-page template

Put a working preview and a concise description near the top. Supply the HTML and CSS in the delivered HTML, with separate copy controls. Include the required base styles, effect rules, and reduced-motion rules.

Explain the implementation's key mechanism, then show how to change its color, size, timing, and radius. Document hover, keyboard focus, touch behavior, and any modern CSS features it needs. Test browser support before making compatibility claims.

Add a parent collection link, a relevant guide, and two to four alternatives with an explanation of their differences. There is no required word count. The page should solve the implementation task without filler.

Keep “Copy prompt” as a useful secondary feature. The code and explanation should remain accessible without an interaction. Google states that its renderer does not interact with pages to reveal content. [Google's lazy-content guidance](https://developers.google.com/search/docs/crawling-indexing/javascript/lazy-loading) supports this design.

## 6. Build internal navigation around these pages

The current card is an `<article role="button">` with a JavaScript click handler (`src/pages/index.astro:84`). Keep the article as a container. Give its heading a real anchor to the effect page. Keep preview, copy, and prompt actions as separate buttons. Do not put nested interactive controls inside an all-card link.

Use this navigation pattern:

1. Link from the homepage to all published collections and the first effect pages.
2. Link from each collection to its relevant effect pages.
3. Link from each effect to its primary collection, a guide, and useful alternatives.
4. Link from guide examples to their implementations and relevant collections.
5. Show visible breadcrumbs that reflect this hierarchy.

Use descriptive anchor text such as “CSS border-draw button” where it reads naturally. Google recommends anchors with real `href` values and contextual internal links. [Google's link guidance](https://developers.google.com/search/docs/crawling-indexing/links-crawlable) describes these requirements.

The intended journey is `Homepage → Collection → Effect`. Every published effect should be reachable within that journey. Do not depend on a sitemap or a search box as its only route.

Keep the quick-copy modal for gallery visitors. A separate “View code and details” link can open the permanent page. Hash links can help users jump within a gallery, but they do not supply separate search pages.

Keep existing gallery coverage during the first release. If the gallery later needs pagination, generate persistent page URLs and real next/previous anchors. Do not hide most effects behind an interaction-only “Load more” control.

## 7. Add guides with a distinct purpose

| Proposed guide | Questions to answer | Related pages |
|---|---|---|
| `/guides/css-button-hover-effects/` | How do transitions, transforms, and pseudo-elements create hover effects? Why does a transition fail? | Sliding fill, border draw, shine sweep |
| `/guides/accessible-button-animations/` | How should focus, reduced motion, touch, active, and disabled states behave? | Pulse, glitch, arrow push |
| `/guides/customize-css-buttons/` | How do CSS variables control color, timing, dimensions, and radius? | Several different effect families |

Create these as original worked explanations. Generic introductions with the same gallery embedded underneath add little value. Google's guidance favors content that helps the intended audience complete a task. [Google's helpful-content guidance](https://developers.google.com/search/docs/fundamentals/creating-helpful-content) supports this approach.

A real button generator is a later opportunity. Controls for text, colors, border radius, timing, and effect selection could create a useful reference people share. Do not publish an empty generator landing page just to target that phrase.

React or Tailwind versions can follow if demand appears. Add correct, tested code tabs to existing effect pages first. Avoid a full matrix of effect × framework × color pages with only superficial differences.

## 8. Metadata, indexing rules, and structured data

The existing metadata is a strength. The title, description, language, viewport, canonical, and social image are present. Improve titles as pages gain specific purposes:

| Page | Suggested title |
|---|---|
| Homepage | `99 CSS Animated Buttons & Hover Effects | Colorion` |
| Glow collection | `CSS Glow & Neon Buttons: Examples and Code | Colorion` |
| Glow effect | `CSS Glow Button: Demo and HTML/CSS Code | Colorion` |
| Accessibility guide | `Accessible CSS Button Animations: Focus and Reduced Motion` |

For the homepage, a suitable description is: “Explore 99 animated CSS buttons with live hover previews. Copy HTML and CSS for glow, fill, border, and 3D effects. Free under the MIT license.” Only use this wording once the stated HTML-copy behavior exists.

Derive counts from the data instead of hardcoding 99 in multiple titles. Add `og:url` for consistent sharing. Use a specific social image where it helps an effect page communicate its visual result. These changes support presentation. They do not create new search demand.

Use one clear H1 per template. Add an H2 above the homepage gallery, then use H3 for card headings. The skipped heading level is an accessibility and organization issue, not evidence of a ranking penalty. Google recommends descriptive, concise, page-specific titles. [Google's title guidance](https://developers.google.com/search/docs/appearance/title-link) explains how it uses them.

| URL type | Proposed indexing treatment |
|---|---|
| Homepage, selected collections, useful effects and guides | Indexable, self-canonical, included in sitemap |
| Equivalent referral or tracking URLs | Canonical to the clean content URL |
| Arbitrary color, duration, radius, and sort states | Keep as client state or fragments when practical |
| Internal search | Exclude from sitemap. If server routes exist, return a crawlable `noindex` directive |
| Missing effects or empty unsupported combinations | Return 404 |
| HTML/CSS/React tabs on the same example | Prefer one URL unless a separate page supplies substantial independent value |

Do not canonicalize useful collection or effect pages to the homepage. Do not block a page in robots while expecting Google to read its `noindex`. Canonicals are signals for equivalent pages, not a cure for a nonexistent route. [Google's canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) explains the distinction.

If filters arrive, curate a small set of indexable collections. Avoid generating every tag, color, framework, and motion combination as a crawlable URL. [Google's guidance on faceted navigation](https://developers.google.com/crawling/docs/faceted-navigation) covers this risk.

Add `BreadcrumbList` where visible breadcrumbs exist. Other accurate semantic markup is optional and lower priority. Do not mark free code examples as products with invented ratings. Do not budget work for FAQ rich results. Google ended that feature in May 2026. Useful questions and answers still belong in the content. See the [current breadcrumb documentation](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb) and [Google's documentation changelog](https://developers.google.com/search/updates).

## 9. Make the copied product match its claims

The page says every snippet respects `prefers-reduced-motion`. The reduced-motion guard exists in `liveCss`, but `snippets` contains only `BTN_BASE` and the effect rules (`src/data/buttons.ts:466` and `:482`). A visitor who copies CSS alone does not receive that guard.

Add the guard to the actual exported snippet. Include pseudo-elements where their transitions need control. The effect selectors use `:hover`, while prompts refer to hover/focus behavior. Supply suitable `:focus-visible` states and test keyboard use before promoting the examples as accessible.

These are product-quality fixes with an indirect SEO benefit: the examples better satisfy the promise of the page. They are not standalone ranking factors. Add accessible native controls to the new page templates, and avoid making a simulated button contain unrelated interactive actions.

Lighthouse also found low contrast on 99 card-number labels and a label/name mismatch on the card controls. The contrast example was 4.46:1 against a 4.5:1 requirement. Correct these during the card redesign.

Add a real license file and a visible license link. The interface and README say MIT, but the repository contains no license file. Confirm the code's ownership and intended license before adding it. A brief author/about page can explain who maintains the examples and how they are tested. This supports trust and reuse.

## 10. Preserve performance while expanding

The current page performs well in the lab. Its live HTML is about 178 KB before compression and 23 KB with gzip. The initial copy-data JSON is deferred. Do not inline the complete 361 KB JSON payload into every collection page merely to expose more text.

Render the selected effect's HTML and CSS on its detail page. Keep lightweight previews on collections. The global stylesheet contains about 52.5 KB of raw legacy loader rules between lines 360 and 2143. No loader component appears in the current homepage. Remove or isolate that block after checking shared keyframe references.

An effect page should need its own effect styles and common site styles. Avoid sending all 99 effects to every detail page. Reconsider the current all-inline CSS strategy once several pages share a stable stylesheet. Measure the result before changing the strategy. The current 99 performance score makes this a maintenance improvement with lower urgency than the content hierarchy.

For field checks, use Search Console or real-user measurements. Target good LCP, INP, and CLS at the 75th percentile. This audit did not measure field INP. [Google's Core Web Vitals documentation](https://developers.google.com/search/docs/appearance/core-web-vitals) defines the metrics and thresholds.

## 11. Competitive and Colorion-network opportunities

[Uiverse's button collection](https://uiverse.io/buttons) links cards to individual posts and uses tags for discovery. [Hover.css](https://ianlunn.github.io/Hover/) groups effects by technique and links to setup and tutorial resources. [CSS Scan's button gallery](https://getcssscan.com/css-buttons-examples) shows that a single gallery can also be useful. A hierarchy is an opportunity to serve more distinct tasks, not a prerequisite for any ranking.

The site's useful differentiators are the focused pure-CSS scope, simple theming, copyable implementations, and coding-agent prompts. Improve the correctness of those exports, then explain their advantages through working examples. A larger example count alone is a weak reason to choose the site.

Keep topic ownership clear across Colorion:

| Host | Suggested primary scope |
|---|---|
| Animated Buttons | Pure-CSS button hover effects and practical implementations |
| Gradient Buttons | Gradient button styles and gradient-specific tooling |
| Kinetics | Spring motion, pointer interaction, JavaScript and React motion examples |
| CSS Loaders | Loading animations and loader implementations |

This is an editorial recommendation, not a diagnosis of existing keyword cannibalization. Search Console data across the properties is necessary for that diagnosis.

Add contextual links from relevant existing Colorion content to the new pages. For example, an appropriate palette page can reference a glow-button implementation that demonstrates contrast and theming. Use those links where they help the visitor. Repeated menu links have a different purpose.

Do not move this working subdomain as the first SEO action. A migration needs evidence that its benefit outweighs redirect, content-overlap, and indexing costs. The proposed hierarchy works on the current domain.

These are planning estimates for one developer who knows the project. Editorial review and hosting access can change them.

|---|---|---|---|
| 1 | Correct missing-route behavior, robots, sitemap, and tooltip link | 0.5–1 day | Live endpoint and status checks pass |
| 2 | Add stable data identifiers, collection and effect templates, native card links, and complete exports | 2–3 days | Direct routes work. Code and explanations exist in initial HTML |

| 4 | Add the other collections, three guides, and contextual network links | 3–5 days | Each new page serves a distinct task |
| 5 | Refine the content from actual query and usage data | Review after 4, 8, and 12 weeks | Evidence supports further pages, revisions, or consolidation |

Implementation should extend the existing data model with stable IDs, slugs, summaries, primary collections, related effects, and editorial notes. The current array position determines effect classes and snippet keys. Keep that mapping stable while separating public slugs from array order.

Likely project changes are `src/pages/effects/[slug].astro`, `src/pages/collections/[slug].astro`, guide routes, shared card/preview/code components, metadata extensions, `public/robots.txt`, and `src/pages/404.astro`. Generate these from shared data so related links, route lists, counts, and sitemaps agree.

Before the release, check the direct URL, title, canonical, H1, source HTML, code export, and inbound links for each page type. Check a nonexistent effect as well. Repeat the mobile lab check after template changes. Inspect representative live URLs in Search Console after deployment.

Record a baseline before launch:

- Organic clicks and impressions by page and query over the last 90 days.
- Non-brand queries for the relevant effect families.
- Indexed canonical pages, duplicate classifications, and soft-404 reports.
- Organic landing pages that lead to a successful code or prompt copy.
- Core Web Vitals where enough field data exists.

Plausible already appears in the layout. Add successful-copy events with effect ID, page type, and export type. Keep Search Console as the source for Google query data. Code copies measure whether the new traffic achieves the site's purpose. They are not a claimed ranking signal.

Compare rolling 28-day periods and prior-year data where available. Separate old homepage traffic from new-page traffic and brand from non-brand queries. Watch whether new pages add useful visits or merely split impressions across similar URLs. Merge redundant pages if the evidence supports it.

The desired early outcome is clean discovery and useful new landing pages. The traffic outcome must follow from measured demand, indexing, relevance, and links. This audit does not support a percentage-growth promise.

## Audit limits and evidence

One Lighthouse run used simulated mobile throttling. The public PageSpeed API returned HTTP 429, so it supplied no field assessment. Some requests with Python's default user agent returned 403. Requests with the audit user agent and Lighthouse succeeded. This does not establish whether verified Googlebot encounters restrictions.

The local build and live page agree on the main content and metadata. The live page includes an extra script. No conclusion about Google's current indexed-page count follows from a public search or the build count.

The companion JSON file stores the compact build, HTTP, and Lighthouse evidence. The pre-existing README edit was outside this audit's changes.
